# wxapkg 解包原理详解

> 本文分析本项目如何把明文 `.wxapkg` 包还原成文件目录。这里的“解包”指读取包头、文件索引、offset/size，再把每个内部文件切出来写入磁盘。

## 1. 解包发生在哪里

解包核心在 `wechat/core.go` 的 `Unpacker`。

完整调用链：

```text
AppService.UnpackWxapkgItem(item, options)
  -> wechat.NewUnpacker(itemPtr, &options)
  -> Unpacker.UnpackWithStatusCallback(callback)
  -> Unpacker.init()
  -> Unpacker.analyzeAll()
  -> Unpacker.analyze(fileData, wxapkgFilePath)
  -> Unpacker.unpack(20, callback)
```

主要职责分工：

| 方法 | 作用 |
| --- | --- |
| `init` | 确定输入 `.wxapkg` 文件列表和输出目录 |
| `analyzeAll` | 读取每个包，必要时解密，然后解析索引 |
| `analyze` | 按 `.wxapkg` 明文结构读取文件表 |
| `unpack` | 根据 offset/size 切出文件内容，并发写入磁盘 |

## 2. 输入可以是什么

前端支持三类输入：

1. 单个 `.wxapkg` 文件。
2. 单个小程序目录。
3. 微信小程序安装目录。

后端最终都会转成 `WxapkgItem`：

```go
type WxapkgItem struct {
    UUID            string
    WxId            string
    Location        string
    EncryptKey      string
    Size            int64
    IsDir           bool
    LastModifyTime  int64
    WxapkgFilePaths []string

    UnpackStatus       StatusType
    UnpackCurrent      int64
    UnpackTotal        int64
    UnpackProgress     float64
    UnpackCurrentFile  string
    UnpackSavePath     string
    UnpackErrorMessage string
}
```

如果 `item.IsDir == true`，`init()` 会递归扫描这个目录下所有后缀为 `.wxapkg` 的文件：

```go
files, err := ListFilesWithExtension(u.item.Location, ".wxapkg")
u.item.WxapkgFilePaths = files
```

如果是单个文件，则：

```go
u.item.WxapkgFilePaths = []string{u.item.Location}
```

这解释了为什么选择“小程序目录”时，一个条目可能对应多个 `.wxapkg` 文件。

## 3. 明文 `.wxapkg` 的整体结构

根据本项目的解析代码，明文 `.wxapkg` 可以抽象成：

```text
┌────────────┬──────────────┬────────────────────┬───────────────┐
│ 包头 Header │ 文件数量      │ 文件索引 Index       │ 文件内容 Body  │
└────────────┴──────────────┴────────────────────┴───────────────┘
```

更具体一点：

```text
0                                         13 14             17 18
┌──────┬────────┬────────────────┬──────────────┬──────┬───────────┬───────────┐
│ BE   │ info1  │ indexInfoLength│ bodyInfoLength│ ED   │ fileCount │ fileIndex │ body...
│ 1B   │ 4B     │ 4B             │ 4B            │ 1B   │ 4B        │ variable  │
└──────┴────────┴────────────────┴──────────────┴──────┴───────────┴───────────┘
```

所有多字节整数都用 Big Endian 读取：

```go
binary.Read(f, binary.BigEndian, &value)
```

## 4. 包头 Header

`analyze()` 首先读取这 14 字节：

```go
var (
    firstMark       uint8
    info1           uint32
    indexInfoLength uint32
    bodyInfoLength  uint32
    lastMark        uint8
)
```

字段含义按代码可归纳为：

| 字段 | 长度 | 当前实现的用途 |
| --- | --- | --- |
| `firstMark` | 1 字节 | 必须是 `0xBE` |
| `info1` | 4 字节 | 读取但未使用 |
| `indexInfoLength` | 4 字节 | 读取但未使用 |
| `bodyInfoLength` | 4 字节 | 读取但未使用 |
| `lastMark` | 1 字节 | 必须是 `0xED` |

校验逻辑：

```go
if firstMark != 0xBE || lastMark != 0xED {
    return nil, errors.New("wxapkg 文件结构不合法")
}
```

所以对本项目来说，`0xBE` 和 `0xED` 是判断明文包结构是否成立的核心标志。

## 5. 文件数量 fileCount

包头之后读取 `fileCount`：

```go
var fileCount uint32
binary.Read(f, binary.BigEndian, &fileCount)
```

它表示文件索引表里有多少个文件条目。

项目做了一个上限保护：

```go
if fileCount > 102400 {
    return nil, errors.Errorf("文件总数量 %d 超出上限 102400", fileCount)
}
```

这个保护很重要，因为如果密钥错误或文件损坏，随机字节可能被解释成一个极大的文件数量，导致内存分配异常或长时间循环。

## 6. 文件索引 Index

每个文件索引条目的结构是：

```text
┌─────────┬──────────────┬────────┬──────┐
│ nameLen │ name         │ offset │ size │
│ 4B      │ nameLen bytes│ 4B     │ 4B   │
└─────────┴──────────────┴────────┴──────┘
```

对应代码：

```go
var nameLen uint32
binary.Read(f, binary.BigEndian, &nameLen)

nameBytes := make([]byte, nameLen)
io.ReadAtLeast(f, nameBytes, int(nameLen))

binary.Read(f, binary.BigEndian, &item.offset)
binary.Read(f, binary.BigEndian, &item.size)
```

### 6.1 nameLen

`nameLen` 是文件名长度，单位是字节。

项目限制：

```go
if nameLen > 1024 {
    return nil, errors.Errorf("文件名长度 %d 超出上限 1024 字节", nameLen)
}
```

这个限制同样可以防止损坏包或错误密钥造成异常内存分配。

### 6.2 name

`name` 是文件在小程序包里的路径。例如：

```text
/app.json
/app.js
/pages/index/index.js
/pages/index/index.json
/pages/index/index.wxml
/pages/index/index.wxss
```

项目后续会把它拼到输出目录下：

```go
item.savePath = filepath.Abs(filepath.Join(u.item.UnpackSavePath, item.name))
```

注意：如果 `item.name` 以 `/` 开头，`filepath.Join` 在不同平台上的行为需要重点关注。当前代码还会做前缀检查，防止最终路径逃出输出目录。

### 6.3 offset

`offset` 是文件内容在整个明文 `.wxapkg` 数据里的起始位置。

本项目把它当作“相对于整个包文件开头的绝对偏移”，因为写出时直接使用：

```go
data := (*d.rawFileData)[d.offset : d.offset+d.size]
```

没有再加上 body 起始地址，也没有使用 `bodyInfoLength` 参与计算。

### 6.4 size

`size` 是文件内容长度。

项目限制单个文件不能超过 10 MB：

```go
if item.size > 10*1024*1024 {
    return nil, errors.Errorf("文件名 %s 标记长度 %d 超出上限 10 MB", item.name, item.size)
}
```

这个限制避免异常包声明一个特别大的文件。但当前实现还没有显式检查：

```text
offset + size <= len(rawFileData)
```

如果 offset/size 损坏，后续切片时可能 panic。这个点适合后续加固。

## 7. 文件条目在内存里如何表示

解析出的索引不会立即写入磁盘，而是保存为：

```go
type WxapkgFileItemStructure struct {
    name     string
    offset   uint32
    size     uint32
    savePath string

    rawFileData *[]byte
    rawFilePath *string
}
```

几个字段的作用：

| 字段 | 作用 |
| --- | --- |
| `name` | 包内文件名 |
| `offset` | 文件内容在包数据中的起始偏移 |
| `size` | 文件内容长度 |
| `savePath` | 文件最终写到磁盘的位置 |
| `rawFileData` | 指向完整明文包数据 |
| `rawFilePath` | 指向原始 `.wxapkg` 文件路径，用于错误提示 |

这里使用 `rawFileData *[]byte` 而不是复制文件内容，是为了避免在解析索引阶段就复制所有文件数据。真正写文件时再切片，内存开销更低。

## 8. 多包合并与重名处理

一个小程序目录下可能有多个 `.wxapkg` 文件。`analyzeAll()` 会把所有包的索引都追加到 `u.files`：

```go
u.files = append(u.files, files...)
```

如果不同包里出现同名文件，项目会重命名后来的文件：

```text
a.txt
a-1.txt
a-2.txt
```

对应代码维护了一个 `fileNameMap`：

```go
for u.fileNameMap[item.name] {
    dot := strings.LastIndex(name, ".")
    if dot == -1 {
        item.name = fmt.Sprintf("%s-%d", item.name, j)
    } else {
        item.name = fmt.Sprintf("%s-%d%s", item.name[:dot], j, item.name[dot:])
    }
    j++
}
u.fileNameMap[item.name] = true
```

这样做的好处是不会互相覆盖。代价是重名文件的来源关系不再那么直观，需要通过原始包路径或文件内容进一步判断。

## 9. 输出路径和目录穿越检查

项目会把包内文件名拼接到输出目录：

```go
item.savePath = filepath.Abs(filepath.Join(u.item.UnpackSavePath, item.name))
```

然后检查：

```go
if !strings.HasPrefix(item.savePath, u.item.UnpackSavePath) {
    return nil, errors.Errorf("文件名 %s 会导致目录穿越", item.name)
}
```

这用于防止包内文件名包含 `../`，把文件写到输出目录之外。

更严谨的写法通常是：

```text
1. 把输出目录和目标路径都转成 clean absolute path。
2. 使用 filepath.Rel(outputDir, targetPath)。
3. 如果相对路径以 ".." 开头，或是绝对路径，则拒绝。
```

当前实现用字符串前缀，思路简单，但在路径边界上不如 `filepath.Rel` 严谨。例如 `/tmp/out2` 也会拥有 `/tmp/out` 前缀。这个点适合后续优化。

## 10. 并发写文件

`unpack(20, callback)` 使用 20 个 worker 并发写文件。

结构如下：

```text
u.files
  -> 生产者 goroutine 逐个发送到 channel
  -> 20 个 worker 并发消费
  -> 创建目录
  -> 根据 offset/size 切出文件
  -> 可选美化
  -> 写入磁盘
  -> 更新进度
```

生产者：

```go
go func() {
    for _, d := range u.files {
        chFiles <- d
    }
    close(chFiles)
}()
```

消费者：

```go
for d := range chFiles {
    dir := filepath.Dir(d.savePath)
    os.MkdirAll(dir, os.ModePerm)

    data := (*d.rawFileData)[d.offset : d.offset+d.size]

    os.WriteFile(d.savePath, data, 0600)

    u.item.IncreaseProgress(d.name)
    callback(u.item)
}
```

并发写出能提高大量小文件的处理速度。由于每个文件写到不同路径，天然适合并发。

## 11. 文件内容如何被切出来

解包最核心的一句是：

```go
data := (*d.rawFileData)[d.offset : d.offset+d.size]
```

这表示 `.wxapkg` 并不是逐个压缩文件的 zip 格式，而更像：

```text
前面是一张文件目录表：
  文件 A -> offset=1000, size=20
  文件 B -> offset=1020, size=80
  文件 C -> offset=1100, size=40

后面是一整块文件内容：
  从 offset 指向的位置切 size 个字节
```

所以这个项目的“解包”本质不是解压缩，而是：

```text
读取索引表 -> 按偏移和长度切片 -> 写回文件系统
```

## 12. 代码美化在解包中的位置

切出文件内容后，写入磁盘前，项目根据扩展名执行可选美化：

```go
var ext = filepath.Ext(d.name)
if ext == ".json" && u.options.EnableJsonBeautify {
    data = PrettyJson(data)
} else if ext == ".html" && u.options.EnableHtmlBeautify {
    data = PrettyHtml(data)
} else if ext == ".js" && u.options.EnableJsBeautify {
    data = PrettyJavaScript(data)
}
```

注意：

- `.json` 默认启用美化。
- `.html` 和 `.js` 默认关闭。
- `.wxml`、`.wxss` 当前不会被特殊美化。
- 美化是在内存里改写 `data` 后再落盘，不会影响原始 `.wxapkg`。

## 13. 进度状态如何更新

解包状态保存在 `WxapkgItem` 里：

```go
UnpackCurrent
UnpackTotal
UnpackProgress
UnpackCurrentFile
UnpackStatus
UnpackErrorMessage
```

在开始写文件前：

```go
u.item.UnpackTotal += int64(len(u.files))
u.item.UnpackStatus = StatusTypeRunning
callback(u.item)
```

每写完一个文件：

```go
u.item.IncreaseProgress(d.name)
callback(u.item)
```

`IncreaseProgress` 会计算百分比：

```go
u.UnpackProgress = float64(u.UnpackCurrent) / float64(u.UnpackTotal) * 100
```

由于有 20 个 worker 同时写文件，项目用 `sync.Mutex` 保护状态更新，避免并发写同一个 `WxapkgItem`。

前端收到后端事件后，会再调用 `GetWxapkgItem(uuid)` 拉取最新状态并刷新 UI。

## 14. 错误处理模型

解包错误大致分两类。

### 14.1 分析阶段错误

发生在真正写文件之前：

- 输出目录转绝对路径失败。
- 输入目录下找不到 `.wxapkg` 文件。
- 文件读取失败。
- 加密文件未启用解密。
- 缺少解密密钥。
- 解密后包头不合法。
- 文件数量、文件名长度、单文件大小超过限制。
- 文件名导致目录穿越。

这些错误会直接设置：

```go
u.item.SetErrorState(err.Error())
callback(u.item)
return
```

### 14.2 写出阶段错误

发生在 worker 里：

- 创建目录失败。
- 写文件失败。

一旦任意 worker 出错，项目会设置 `hasError = true`，之后其他 worker 会尽快停止。

## 15. 当前实现的关键假设

阅读源码时，最好把这些假设记住：

1. 解密后的包一定以 `0xBE` 开头，并且第 14 字节是 `0xED`。
2. 所有整数都是 Big Endian。
3. `offset` 是相对于整个 `.wxapkg` 明文数据的绝对偏移。
4. 包内文件内容没有额外压缩，按 offset/size 切出来就是可写出的文件内容。
5. 同一个小程序目录下可能有多个 `.wxapkg`，项目会合并解析。
6. 同名文件不能覆盖，会自动追加编号。
7. 输出路径必须处于 `UnpackSavePath` 下。

## 16. 推荐的调试观察点

如果你想加深理解，可以在这些位置打日志：

### 16.1 `analyze()` 读取包头后

观察：

```text
firstMark
info1
indexInfoLength
bodyInfoLength
lastMark
fileCount
```

这能验证包结构是否被正确解密。

### 16.2 每次读取文件索引后

观察：

```text
name
offset
size
savePath
```

这能帮助理解 `.wxapkg` 里的文件表如何映射到真实目录。

### 16.3 写文件前

观察：

```text
len(rawFileData)
offset + size
ext
```

这能定位 offset/size 异常、文件扩展名判断、美化开关等问题。

## 17. 可以加固的点

当前项目已经能完成主要解包流程，但还有一些适合学习和改进的地方：

1. 检查所有 `binary.Read` 和 `io.ReadAtLeast` 的 error。
2. 检查 `offset + size <= len(rawFileData)`。
3. 检查 `offset + size` 的整数溢出。
4. 用 `filepath.Rel` 替代字符串前缀做目录穿越判断。
5. 让 worker 数量可配置，或者根据 CPU / 文件数量动态调整。
6. 增加 `.wxml`、`.wxss` 格式化支持。
7. 为 `analyze()` 构造最小 `.wxapkg` 样本单元测试。

## 18. 一句话总结

本项目的解包原理是：先把 `.wxapkg` 明文数据当成一个“包头 + 文件索引 + 文件内容区”的二进制容器读取，文件索引告诉每个文件的名称、起始偏移和长度，程序再按这些 offset/size 从完整包数据中切出内容，并发写回输出目录。
