# wxapkg 项目运行与原理讲解

> 说明：本项目用于学习和研究微信小程序包的文件结构、解密流程和桌面应用实现方式。请只在合法授权范围内使用，不要用于侵权、绕过保护或其他非法场景。

## 1. 这个项目是什么

`wxapkg` 是一个基于 Wails 的桌面工具。它的目标是把微信 PC 端缓存的小程序包，也就是 `.wxapkg` 文件，解析并还原成接近小程序源码目录的文件结构。

从代码结构看，它不是一个命令行解包器，而是一个桌面 GUI：

- Go 后端负责系统目录探测、`.wxapkg` 解密、包结构解析、文件写出和进度事件。
- Vue 前端负责扫描入口、解包配置弹窗、进度展示、结果目录打开等交互。
- Wails 负责把前端页面和 Go 方法绑定在一起，形成一个跨平台桌面应用。

核心代码分布如下：

| 路径 | 作用 |
| --- | --- |
| `main.go` | Wails 应用入口，创建窗口、嵌入前端资源、绑定后端服务 |
| `app.go` | 暴露给前端调用的 Go 服务层，例如扫描、解包、打开目录 |
| `wechat/core.go` | `.wxapkg` 解析、解包状态、并发写文件等核心逻辑 |
| `wechat/util.go` | 解密算法、目录扫描、大小统计、UUID 等工具函数 |
| `wechat/core_macos.go` | macOS 微信小程序缓存路径自动探测 |
| `wechat/core_windows.go` | Windows 微信小程序缓存路径自动探测 |
| `wechat/beautify.go` | JSON、HTML、JavaScript 美化 |
| `frontend/src/App.vue` | 主页面，表格展示、扫描、进度事件监听 |
| `frontend/src/components/ScanDialog.vue` | 扫描小程序入口 |
| `frontend/src/components/UnpackDialog.vue` | 解包配置、进度、成功/失败弹窗 |
| `frontend/src/components/SettingsDialog.vue` | 默认输出目录设置 |

## 2. 如何运行

### 2.1 环境要求

项目根目录的 `go.mod` 指定 Go 版本为 `1.25`，前端使用 Vue 3、Vite、PrimeVue。运行时需要：

- Go
- Node.js / npm
- Wails CLI

安装 Wails CLI：

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@latest
```

安装前端依赖：

```bash
cd frontend
npm install
cd ..
```

### 2.2 开发模式运行

在项目根目录执行：

```bash
wails dev
```

这会启动 Wails 桌面应用，并让前端进入 Vite 热更新模式。日常看效果、调前端、调 Go 绑定方法，都建议用这个命令。

### 2.3 构建发布包

在项目根目录执行：

```bash
wails build
```

构建产物会输出到 `build/bin/`。项目的 `.github/workflows/release.yml` 也使用这个命令分别构建 Windows 和 macOS 版本。

### 2.4 不建议直接 `go run`

`main.go` 里有：

```go
//go:embed all:frontend/dist
var assets embed.FS
```

这表示正式构建时 Go 程序会把 `frontend/dist` 嵌入二进制。仓库里 `frontend/dist` 被 `.gitignore` 忽略，干净检出后通常不存在。因此直接 `go run` 可能会因为找不到嵌入资源而失败。这个项目的正确入口是 Wails。

## 3. 用户使用流程

从用户角度看，一次完整解包流程是：

1. 打开应用。
2. 点击“扫描小程序”。
3. 选择自动扫描，或者手动指定 `.wxapkg` 文件、小程序目录、微信小程序安装目录。
4. 应用生成小程序列表，每一行是一个 `WxapkgItem`。
5. 点击某个条目的解包按钮。
6. 在弹窗里设置：
   - 是否启用解密。
   - 解密密钥，通常就是小程序 ID，例如 `wxabcdef1234567890`。
   - 是否美化 JSON、HTML、JavaScript。
   - 输出目录。
7. 前端调用后端开始解包。
8. 后端通过 Wails 事件持续通知进度。
9. 解包完成后，前端展示输出目录，并可直接打开目录。

对应代码链路：

```text
ScanDialog.vue
  -> App.vue confirmScan()
  -> AppService.ScanWxapkgItem()
  -> wechat.ScanWxapkgItem()

UnpackDialog.vue
  -> App.vue confirmUnpack()
  -> AppService.UnpackWxapkgItem()
  -> wechat.NewUnpacker(...).UnpackWithStatusCallback(...)
  -> runtime.EventsEmit("unpack:progress-changed", item.UUID)
  -> App.vue processProgress()
  -> AppService.GetWxapkgItem(uuid)
```

## 4. 整体架构

### 4.1 Wails 桌面壳

`main.go` 负责创建桌面窗口：

- 标题是“微信小程序解包工具”。
- 默认窗口大小是 `1024x768`。
- `AssetServer` 使用嵌入的 `frontend/dist`。
- `Bind` 把 `AppService` 暴露给前端。

前端生成的绑定文件在 `frontend/wailsjs/go/main/AppService.js` 和 `frontend/wailsjs/go/models.ts` 中。前端调用 `AppService.ScanWxapkgItem(...)` 这类函数时，本质上是在跨进程调用 Go 方法。

### 4.2 Go 服务层

`app.go` 是前端和核心逻辑之间的薄封装层。它主要做几件事：

- 打开系统文件或目录选择框。
- 获取默认微信小程序缓存路径。
- 扫描 `.wxapkg` 条目。
- 启动解包。
- 维护一个 `sync.Map`，用 UUID 保存每个解包任务的最新状态。
- 通过 Wails 事件把进度变化推给前端。

这里采用的是“事件通知 + 主动拉取详情”的模式：

1. 后端解包时更新 `WxapkgItem` 状态。
2. 后端只通过事件发送 UUID。
3. 前端收到 UUID 后，再调用 `GetWxapkgItem(uuid)` 拉取完整状态。

这样事件消息比较轻，前端也能拿到最新状态。

### 4.3 前端页面

前端主要使用 Vue 3 和 PrimeVue：

- `App.vue` 是主页面，保存小程序列表、搜索条件、当前选中项、默认输出目录等状态。
- `ScanDialog.vue` 负责自动扫描和手动指定路径。
- `UnpackDialog.vue` 负责配置解包参数、展示进度、展示结果。
- `SettingsDialog.vue` 把默认输出目录存在浏览器 `localStorage` 中。

前端状态没有接入复杂状态管理库，数据都放在组件内的 `ref`、`reactive`、`computed` 里，项目规模较小时这样足够清晰。

## 5. 自动扫描原理

自动扫描的入口是：

```go
func (a *AppService) GetDefaultPaths() wechat.PathScanResult
```

它实际调用平台相关实现：

```go
var Platform = newPlatform()
```

Go 通过 build tag 选择不同文件：

- macOS：`wechat/core_macos.go`
- Windows：`wechat/core_windows.go`
- 其他系统：`wechat/core_other.go`

### 5.1 macOS 扫描路径

macOS 会检测这些位置：

```text
~/Library/Containers/com.tencent.xinWeChat/Data/.wxapplet/packages
~/Library/Containers/com.tencent.xinWeChat/Data/Documents/app_data/radium/Applet/packages
~/Library/Containers/com.tencent.xinWeChat/Data/Documents/app_data/radium/users/*/applet/packages
```

它覆盖了微信 3.x、微信 4.x、微信 4.x 多用户场景。

### 5.2 Windows 扫描路径

Windows 会检测：

```text
%AppData%\Tencent\xwechat\radium\Applet\packages
%AppData%\Tencent\xwechat\radium\users\*\applet\packages
```

同时还会读注册表：

```text
HKCU\Software\Tencent\WeChat\FileSavePath
```

用于兼容微信 3.x 的文件保存路径。

### 5.3 从安装目录识别小程序

`wechat.ScanWxapkgItem(path, scan)` 有两种模式：

- 如果传入的是单个文件、单个目录，或者 `scan=false`，它直接返回一个条目。
- 如果传入的是安装目录并且 `scan=true`，它遍历一级子目录，只把目录名匹配 `^wx[0-9a-f]{16}$` 的目录识别为小程序。

当目录名本身就是小程序 ID 时，项目会自动把它作为 `EncryptKey`，所以选择“小程序安装目录”时通常不需要手动输入密钥。

## 6. `.wxapkg` 解密原理

核心函数是 `wechat/util.go` 里的：

```go
func decryptWxapkgFile(wxid string, dataByte []byte) ([]byte, error)
```

这个实现采用的是已知的微信 PC 小程序包解密思路：

1. 使用小程序 ID，也就是 `wxid`，作为口令。
2. 使用固定 salt：

```text
saltiest
```

3. 使用 PBKDF2 派生 AES key：

```text
PBKDF2-SHA1(wxid, "saltiest", 1000, 32 bytes)
```

4. 使用固定 IV：

```text
the iv: 16 bytes
```

5. 跳过加密文件前 6 字节，从 `dataByte[6:1030]` 取 1024 字节，用 AES-CBC 解密。
6. 剩余部分用单字节 XOR 还原。XOR key 默认是 `0x66`，如果 wxid 长度足够，则使用 wxid 倒数第二个字符的字节值。
7. 把 AES 解密出的前 1023 字节和 XOR 还原出的剩余数据拼接，得到解密后的 `.wxapkg` 数据。

代码中判断一个包是否已经解密，靠的是 magic byte：

```go
data[0] == 0xBE && data[13] == 0xED
```

如果这个判断成立，就认为当前数据已经是可解析的 `.wxapkg` 结构，不再走解密。

## 7. `.wxapkg` 解包原理

核心逻辑在 `wechat/core.go` 的 `Unpacker`。

### 7.1 初始化

`Unpacker.init()` 会做这些事：

- 把输出目录转成绝对路径。
- 如果输入是目录，就递归找出目录下所有 `.wxapkg` 文件。
- 如果输入是文件，就只处理这个文件。
- 使用前端计算并传入的 `SavePath` 作为最终输出目录。

目录输入比较常见，因为一个小程序目录下可能包含多个 `.wxapkg` 包。

### 7.2 解析所有包

`Unpacker.analyzeAll()` 会逐个读取 `.wxapkg` 文件：

1. `os.ReadFile` 读入完整文件。
2. 判断是否已经解密。
3. 如果未解密并且用户启用了 `EnableDecrypt`，用 `EncryptKey` 解密。
4. 调用 `analyze()` 解析包结构。
5. 把每个包里的文件索引追加到 `u.files`。

如果文件是加密的，但用户没有启用解密，或者没有提供密钥，就会进入错误状态。

### 7.3 包头结构

`analyze()` 按大端序读取 `.wxapkg`：

```text
firstMark        1 byte   期望 0xBE
info1            4 bytes
indexInfoLength  4 bytes
bodyInfoLength   4 bytes
lastMark         1 byte   期望 0xED
fileCount        4 bytes
```

当前实现会校验 `firstMark` 和 `lastMark`，但不会使用 `info1`、`indexInfoLength`、`bodyInfoLength` 做进一步计算。

### 7.4 文件索引结构

接下来循环读取 `fileCount` 个文件索引。每个文件索引大致是：

```text
nameLen  4 bytes
name     nameLen bytes
offset   4 bytes
size     4 bytes
```

其中：

- `name` 是文件在小程序里的路径，例如 `/app.json`、`/pages/index/index.js`。
- `offset` 是文件内容在整个包数据里的起始偏移。
- `size` 是文件内容长度。

解析后不会马上写文件，而是先保存成 `WxapkgFileItemStructure`：

```go
type WxapkgFileItemStructure struct {
    name     string
    offset   uint32
    size     uint32
    savePath string

    rawFileData *[]byte
    rawFilePath *string
}
```

其中 `rawFileData` 指向完整包数据，真正写文件时再通过：

```go
data := (*d.rawFileData)[d.offset : d.offset+d.size]
```

切出单个文件内容。

### 7.5 文件名冲突与安全检查

项目做了几类基础防护：

- `fileCount` 不能超过 `102400`。
- 文件名长度不能超过 `1024` 字节。
- 单个文件标记长度不能超过 `10 MB`。
- 输出路径必须仍然在解包目录下，避免 `../` 造成目录穿越。
- 如果多个包里出现同名文件，会自动重命名为 `a-1.txt`、`a-2.txt` 这类形式。

这里有一个值得注意的细节：路径穿越检查使用的是字符串前缀：

```go
strings.HasPrefix(item.savePath, u.item.UnpackSavePath)
```

学习时可以进一步思考更严谨的做法，例如先统一清理路径，再用 `filepath.Rel` 判断相对路径是否逃逸。

### 7.6 并发写出

`Unpacker.unpack(thread int, callback func(item *WxapkgItem))` 用固定 `20` 个 worker 并发写文件：

1. 一个 goroutine 把所有文件任务送进 channel。
2. 20 个 worker 从 channel 取文件。
3. 创建目录。
4. 从包数据里切出文件内容。
5. 按扩展名选择是否美化。
6. 写入磁盘。
7. 更新进度并回调。

解包过程中的状态由 `WxapkgItem` 保存：

```go
UnpackStatus
UnpackCurrent
UnpackTotal
UnpackProgress
UnpackCurrentFile
UnpackSavePath
UnpackErrorMessage
```

状态更新通过互斥锁保护，避免多个 worker 同时修改进度。

## 8. 代码美化原理

美化逻辑在 `wechat/beautify.go`：

- JSON 使用 `github.com/tidwall/pretty`。
- HTML 使用 `github.com/yosssi/gohtml`。
- JavaScript 使用 `github.com/ditashi/jsbeautifier-go/jsbeautifier`。

HTML 里还有一个额外处理：它会用正则找出 `<script>...</script>` 片段，并对其中的 JavaScript 再做一次格式化。

前端默认启用 JSON 美化，HTML 和 JavaScript 美化默认关闭。这样可以减少大 JS 文件格式化带来的耗时，也避免对某些压缩代码造成额外扰动。

## 9. 输出目录规则

前端在开始解包前会调用：

```go
AppService.ComputeSavePath(outputDir, wxapkgPath)
```

规则是：

1. 把用户选择的输出目录转成绝对路径。
2. 取输入路径的最后一段文件名或目录名。
3. 去掉扩展名。
4. 拼出：

```text
<输出目录>/<输入名>_unpacked
```

例如：

```text
输入文件: /tmp/app.wxapkg
输出目录: /Users/me/Desktop
最终目录: /Users/me/Desktop/app_unpacked
```

如果输入是一个小程序目录，最终目录会使用目录名。

前端还会把默认输出目录和上次输出目录存在 `localStorage`，key 是：

```text
wxapkg:output-directory:preference:v1
```

## 10. 前后端通信细节

Wails 会生成前端可调用的 JS 包装函数。比如：

```ts
import * as AppService from '../wailsjs/go/main/AppService';
```

前端可以直接调用：

```ts
AppService.ScanWxapkgItem(path, scan)
AppService.UnpackWxapkgItem(item, options)
AppService.GetWxapkgItem(uuid)
```

Go 后端向前端推送进度时使用：

```go
runtime.EventsEmit(ctx, "unpack:progress-changed", item.UUID)
```

前端监听：

```ts
window.runtime.EventsOn("unpack:progress-changed", (uuid: string) => {
  processProgress(uuid)
})
```

收到事件后，前端不会直接相信事件里有完整数据，而是通过 UUID 再向后端取最新状态。这种方式降低了事件数据量，也避免大对象频繁序列化。

## 11. 发布流程

`.github/workflows/release.yml` 定义了自动发布流程：

- 推送 `v*` tag 时触发。
- Windows 使用 `wails build` 构建 `.exe`。
- macOS 使用 `wails build -platform darwin/universal` 构建通用架构 app。
- Windows 产物会额外用 UPX 压缩。
- 最后用 GitHub Release 上传构建产物。

本地开发时不需要关心这条流程，除非你要研究如何发版。

## 13. 可以继续深入的点

这个项目适合继续研究几个方向：

- `.wxapkg` 文件格式：包头字段 `info1`、`indexInfoLength`、`bodyInfoLength` 在当前实现里没有进一步使用，可以结合参考资料继续验证它们的意义。
- 解密算法来源：当前实现沿用了公开资料中的 PC 小程序包解密方式，可以用样本文件对比解密前后的 magic byte 和文件索引。
- 安全性增强：路径穿越检查、offset/size 边界检查、错误恢复策略都可以继续加固。
- CLI 化：核心逻辑已经在 `wechat` 包中，理论上可以很容易增加一个命令行入口，方便批处理。
- 测试补齐：目前没有测试文件，可以构造一个极小 `.wxapkg` 样本来测试 `analyze()` 和输出逻辑。

## 14. 一句话总结

这个项目的本质是：用 Wails 做一个桌面外壳，自动找到微信缓存的小程序目录，按已知算法把加密 `.wxapkg` 还原为明文包，再读取包内文件索引，根据 offset 和 size 把每个文件切出来，最后按原始路径写入输出目录。
