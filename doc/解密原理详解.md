# wxapkg 解密原理详解

> 本文只分析本项目源码中的解密实现，重点解释数据从“加密 `.wxapkg` 文件”变成“可解析包结构”的过程。

## 1. 解密发生在哪里

解密不是单独暴露成命令，而是嵌在解包流程里。入口链路是：

```text
frontend/src/components/UnpackDialog.vue
  -> AppService.UnpackWxapkgItem(item, options)
  -> wechat.NewUnpacker(itemPtr, &options)
  -> Unpacker.UnpackWithStatusCallback(...)
  -> Unpacker.analyzeAll()
  -> decryptWxapkgFile(wxid, fileData)
```

关键代码位置：

- `app.go`：`UnpackWxapkgItem` 接收前端传来的解包选项。
- `wechat/core.go`：`analyzeAll` 决定是否需要解密。
- `wechat/util.go`：`decryptWxapkgFile` 执行真正的字节级解密。

## 2. 项目如何判断文件是否已经解密

`wechat/core.go` 中的判断函数是：

```go
func (u *Unpacker) isDecryptedWxapkgFile(data []byte) bool {
    if len(data) < 13 {
        return false
    }

    return data[0] == 0xBE && data[13] == 0xED
}
```

它检查两个位置：

| 位置 | 期望值 | 含义 |
| --- | --- | --- |
| `data[0]` | `0xBE` | `.wxapkg` 明文包头的 firstMark |
| `data[13]` | `0xED` | `.wxapkg` 明文包头的 lastMark |

如果这两个字节都匹配，项目认为文件已经是明文 `.wxapkg`，可以直接进入包结构解析。

如果不匹配，则认为它是加密包，需要满足两个条件才会继续：

1. 用户在解包配置中启用了 `EnableDecrypt`。
2. 当前条目有 `EncryptKey`，也就是小程序 ID。

否则会直接报错：

```text
小程序文件 '<path>' 为加密文件，请在解包配置中启用解密
小程序文件 '<path>' 为加密文件，未设置解密密钥
```

一个实现细节：这里的长度判断应当是 `len(data) < 14` 更严谨。当前代码写成 `< 13`，如果文件刚好 13 字节，会访问 `data[13]` 导致越界。实际 `.wxapkg` 文件远大于这个长度，所以正常使用中很难触发，但这是阅读源码时值得注意的边界问题。

## 3. 解密密钥是什么

本项目把小程序 ID 当作解密口令。小程序 ID 形如：

```text
wxabcdef1234567890
```

代码中的正则是：

```go
^wx[0-9a-f]{16}$
```

密钥来源有两种：

1. 自动扫描微信小程序安装目录时，目录名本身通常就是小程序 ID，项目会自动填到 `EncryptKey`。
2. 手动选择单个 `.wxapkg` 文件或单个小程序目录时，前端会让用户手动输入小程序 ID。

前端 `UnpackDialog.vue` 打开时，如果条目里有 `WxId` 或 `EncryptKey`，会自动回填到解密密钥输入框。

## 4. 加密文件的分段模型

本项目的 `decryptWxapkgFile` 把加密数据切成三段理解：

```text
┌──────────────┬──────────────────────────┬──────────────────────┐
│ 前 6 字节     │ 接下来的 1024 字节        │ 剩余全部字节          │
│ data[0:6]    │ data[6:1030]             │ data[1030:]          │
└──────────────┴──────────────────────────┴──────────────────────┘
     丢弃              AES-CBC 解密              单字节 XOR 还原
```

对应代码：

```go
blockMode.CryptBlocks(originData, dataByte[6:1024+6])

afData := make([]byte, len(dataByte)-1024-6)
for i, b := range dataByte[1024+6:] {
    afData[i] = b ^ xorKey
}

originData = append(originData[:1023], afData...)
```

也就是说：

- 前 6 字节不会进入明文结果。
- `data[6:1030]` 使用 AES-CBC 解密。
- `data[1030:]` 使用 XOR 逐字节还原。
- 最终结果取 AES 解密结果的前 1023 字节，再拼接 XOR 还原结果。

这里有一个不太直观的点：AES 解密出来是 1024 字节，但项目只保留 `originData[:1023]`。这意味着最终明文长度不是 `len(dataByte)-6`，而是：

```text
1023 + (len(dataByte) - 1030) = len(dataByte) - 7
```

这是该公开解密算法常见实现里的处理方式。阅读代码时可以把它理解为：加密包头部有额外扰动字节，解密后还要丢掉一个字节，才能让明文 `.wxapkg` 的 magic byte 对齐到 `data[0] == 0xBE`。

## 5. AES 部分如何工作

AES 部分用于还原明文包开头的 1023 字节。

### 5.1 派生 AES key

代码：

```go
dk := pbkdf2.Key([]byte(wxid), []byte(salt), 1000, 32, sha1.New)
```

参数如下：

| 参数 | 值 |
| --- | --- |
| 口令 | 小程序 ID，也就是 `wxid` |
| salt | `saltiest` |
| 迭代次数 | `1000` |
| key 长度 | `32` 字节 |
| hash | SHA-1 |

因为 key 长度是 32 字节，所以这里实际使用的是 AES-256。

### 5.2 创建 CBC 解密器

代码：

```go
block, _ := aes.NewCipher(dk)
blockMode := cipher.NewCBCDecrypter(block, []byte(iv))
```

IV 是固定字符串：

```text
the iv: 16 bytes
```

这个字符串刚好 16 字节，符合 AES block size。

### 5.3 解密 1024 字节

代码：

```go
originData := make([]byte, 1024)
blockMode.CryptBlocks(originData, dataByte[6:1024+6])
```

AES-CBC 要求输入长度是 16 的整数倍。1024 正好是 `16 * 64`，所以可以直接调用 `CryptBlocks`。

这一步只处理加密文件的头部区域，因为 `.wxapkg` 解析最关键的包头和索引信息都位于文件前段。还原这部分后，后续才能读到 `0xBE`、`0xED`、文件数量、文件名、offset、size 等结构。

## 6. XOR 部分如何工作

除了前 1024 字节，剩下的数据使用单字节 XOR。

代码：

```go
var xorKey = byte(0x66)
if len(wxid) >= 2 {
    xorKey = wxid[len(wxid)-2]
}

for i, b := range dataByte[1024+6:] {
    afData[i] = b ^ xorKey
}
```

XOR key 的规则：

| 情况 | XOR key |
| --- | --- |
| `wxid` 长度小于 2 | `0x66` |
| `wxid` 长度大于等于 2 | `wxid` 倒数第二个字符的字节值 |

例如：

```text
wxid = wxabcdef1234567890
倒数第二个字符 = 9
xorKey = byte('9') = 0x39
```

XOR 的特点是同一个操作既能加密也能解密：

```text
plain  ^ key = cipher
cipher ^ key = plain
```

所以项目只需要逐字节执行 `b ^ xorKey`，就能把后半部分还原出来。

## 7. 解密结果如何进入解包流程

`analyzeAll` 的流程可以概括为：

```text
读取 .wxapkg 文件
  -> 判断是否已解密
  -> 如果未解密，检查用户是否启用解密
  -> 检查是否有 wxid
  -> decryptWxapkgFile(wxid, fileData)
  -> analyze(fileData, wxapkgFilePath)
```

解密成功后，项目不会把明文包写到磁盘作为中间文件，而是直接在内存中继续解析。

这一点很重要：

- 输入文件不会被修改。
- 没有临时明文 `.wxapkg` 文件。
- 后续的文件索引和文件内容都来自内存里的 `fileData`。

## 8. 解密正确性的验证点

一个 `.wxapkg` 是否被正确解密，可以用以下信号判断：

1. 解密后的第 1 个字节是 `0xBE`。
2. 解密后的第 14 个字节，也就是下标 `13`，是 `0xED`。
3. 后续 `analyze()` 能成功读取 `fileCount`。
4. 文件索引中的 name、offset、size 能正常解析。
5. 输出目录里能得到 `app.json`、页面 `.js/.json/.wxml/.wxss` 等小程序文件。

如果密钥错误，通常会出现：

- magic byte 不匹配，报“wxapkg 文件结构不合法”。
- 文件数量异常，触发 `文件总数量 ... 超出上限`。
- 文件名长度异常，触发 `文件名长度 ... 超出上限`。
- 后续 offset/size 切片异常，严重时可能导致运行时 panic。

## 9. 当前实现的边界条件和风险点

### 9.1 加密文件长度没有提前检查

`decryptWxapkgFile` 直接访问：

```go
dataByte[6:1024+6]
dataByte[1024+6:]
```

如果输入文件小于 1030 字节，会发生切片越界。更稳妥的做法是在解密前检查：

```go
if len(dataByte) < 1030 {
    return nil, errors.New("加密 wxapkg 文件长度不足")
}
```

### 9.2 没有重新校验解密后的 magic byte

当前流程是：

```text
decryptWxapkgFile(...)
  -> analyze(...)
```

`analyze()` 会校验 magic byte，所以最终仍会发现解密错误。但如果在解密后立即检查一次，可以给出更明确的错误，例如“密钥错误或文件不是受支持的加密格式”。

### 9.3 AES 错误被忽略

代码里：

```go
block, _ := aes.NewCipher(dk)
```

由于 `dk` 固定是 32 字节，正常不会出错。但从编码习惯上看，仍然建议处理 error，让函数更自解释。

### 9.4 XOR key 使用字节而不是字符语义

`wxid[len(wxid)-2]` 取的是字符串底层字节。由于小程序 ID 只包含 ASCII 字符，这没有问题。如果未来输入允许非 ASCII，这种写法就需要重新考虑。

## 10. 用伪代码理解完整解密

```text
function decrypt(wxid, encrypted):
    salt = "saltiest"
    iv = "the iv: 16 bytes"

    aesKey = PBKDF2_SHA1(
        password = wxid,
        salt = salt,
        iterations = 1000,
        keyLength = 32
    )

    aesPart = encrypted[6 : 1030]
    aesPlain = AES_256_CBC_Decrypt(aesPart, aesKey, iv)

    if len(wxid) >= 2:
        xorKey = byte(wxid[-2])
    else:
        xorKey = 0x66

    xorPart = encrypted[1030:]
    bodyPlain = each byte in xorPart XOR xorKey

    return aesPlain[0:1023] + bodyPlain
```

## 11. 一句话总结

本项目的解密逻辑可以理解为：用小程序 ID 经 PBKDF2 派生出 AES-256 key，先解密文件头部 1024 字节，再用小程序 ID 倒数第二个字符作为 XOR key 还原剩余内容，最后拼成明文 `.wxapkg` 包，让后续解包器能按 `0xBE ... 0xED` 的包头结构继续解析。
